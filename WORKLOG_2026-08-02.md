## 2. Bugs found and fixed

### 2.1 Signal truncation silently dropped whole evidence sources

**File:** `agentic_estimation/layer_2/pillar_extractors.py`

`_signals_block()` capped the combined prompt at `_MAX_TOTAL_CHARS = 12000`
and **`break`s** once the budget is exceeded — dropping every remaining
signal entirely rather than truncating it. Signals are iterated in dict
insertion order (= fetch order), which has no pillar awareness.

Consequence: `bhrrc` (Business & Human Rights Resource Centre — the single
dedicated source for Social labour/human-rights evidence) sits 14th in fetch
order and was being dropped on essentially every run. Verified live on Apple:
`bhrrc` absent from the prompt, **0 Social claims extracted**, despite the raw
signal containing textbook `human_rights_incident` material (DRC cobalt,
child labour allegations).

**Fix:** raised to `_MAX_CHARS_PER_SIGNAL = 4000`, `_MAX_TOTAL_CHARS = 60000`
(measured typical total is ~33K chars across ~22 signals, so nothing drops;
the cap remains as a backstop against a runaway fetch).

**Result:** Apple went 0 → 3 Social claims (2× `labor_controversy`,
1× `human_rights_incident`). Samsung's Social pillar went from a bare
country-baseline score to 4 real contributions.

### 2.2 Hardcoded downward bias in the holistic scoring prompt

**File:** `agentic_estimation/layer_3/scoring_agent.py`

`_SCORE_PROMPT` contained two instructions that systematically pushed scores
below baseline whenever evidence was thin:

```
- If evidence for a pillar is thin or absent, score near 45–55 (slightly below
  average to reflect uncertainty)
- Be conservative: companies with limited disclosures likely underperform undisclosed
```

Since thin evidence is the common case, this penalised absence of data as if
it were evidence of poor performance — and the formula scorer does the
opposite (reverts to the neutral country baseline). A large part of the
formula-vs-LLM spread was this disagreement, not a real signal.

**Fix:** replaced with an explicit instruction to use the country baseline
when evidence is thin, and to penalise only on evidence of actual problems.

**Result (verified live):** Honor's Social went 50.0 → 75.3, now correctly
anchored to the China baseline instead of a punitive guess. Vivo's reasoning
additionally caught that its Social evidence belonged to *Vivo Energy* — a
different company — and correctly declined to use it.

### 2.3 Two more tight truncation limits (found by audit)

- `scoring_agent.py::_build_signals_block` — 600 chars/source, feeding the
  live holistic vote **and** `metric_estimation_agent` (which imports it).
  Raised to 4000.
- `evaluator_agent.py` — an independently-defined **duplicate** of the same
  function that had drifted to an even tighter 500 chars. Deleted the copy
  and imported the shared one, so the two can't diverge again.

Neither silently dropped whole sources (unlike 2.1) — they clipped each
source — but 600/500 chars is severe for sources carrying 1000–2900 chars.

### 2.4 `company_evidence_claims` accumulating duplicate rows

**Files:** `agentic_estimation/layer_2/pillar_extractors.py`,
`agentic_estimation/layer_2/ratio_estimator.py`

Two independent writers (`persist_claims()`, `save_ratio_estimates()`) both
did a bare `INSERT` with no `ON CONFLICT` and no delete-before-insert. The
table has **no unique constraint**, so every rerun silently appended on top
of prior runs. After three runs: Samsung 37 claim rows, Apple 43, where a
single run produces 11–20.

**Fix:** both writers now `DELETE` their own rows for that company (scoped by
`produced_by`, so neither clobbers the other) inside the same transaction as
the inserts.

**Cleanup:** purged 107 stale rows; per-company counts now reflect one run.

**Severity note:** this was *latent*, not live. The scoring path uses
in-memory claims from the current run, so persisted scores were never
corrupted. The only reader that would have been affected —
`formula_estimator.load_claims()` — currently has zero callers.

### 2.5 `val` shadowing broke the Pillar Metrics tab

**File:** `demo_ui/frontend2.0.js`

A local `const val` (a display string) inside `drawMet()` shadowed the
module-level `val()` formatting function, throwing `val is not a function`
and blanking the whole tab. Renamed the local to `disp`.

## 3. Codebase audit (two parallel agents)

Swept `layer_1`–`layer_4` for the same two bug classes.

**Truncation / silent-drop:** `pillar_extractors.py` is the **only** place in
the codebase with the dangerous "running total + `break` = drop whole source"
pattern. Everything else clips per item. Confirmed clean: `signal_agent.py`,
`enforcement_collector.py`, `governance_collector.py`, `facility_extractor.py`,
`sec_filings.py`, `evidence_filters.py`, `critic_panel.py`, and the rest of
layer_3/layer_4.

**Bare INSERT:** confined to `company_evidence_claims` (both writers now
fixed). Every other company-keyed table already has a unique constraint *and*
a working `ON CONFLICT` upsert — `company_metric_values`,
`company_esg_signals`, `climate_trace_*`, `market_climate_trace_mapping`,
`country_esg_baseline`, `company_metadata`.

## 5. Open issues

### 5.1 Formula and LLM votes still disagree structurally on Social

Even after both fixes, the two scorers land far apart on Social for several
companies (Samsung formula 82.2 vs LLM 45.0 → 37-point spread). This is not a
data bug — both scorers see the same evidence. The formula treats negative
claims as bounded point deductions from a baseline; the LLM weighs "multiple
credible negative stories" much more heavily as a qualitative judgment.

Options not yet explored: show the holistic scorer the formula's extracted
claims so it can agree/disagree with specifics rather than voting blind; or
reweight the blend per pillar.

### 5.2 WikiRate data is unreliable for large companies

WikiRate's keyword-based metric-card matching returns wrong-scale values:
Apple's `employee_count` came back as **4.003** (real: ~164,000), and a
`scope_1_emissions` row of 10.0 that is almost certainly a mismatched card.
Three unrelated companies (Apple, Samsung, Huawei) all returned identical
0.0 for energy, water, turnover, and whistleblower.

**Current mitigation:** `build_esg_json.py` excludes all WikiRate rows
entirely. Upright and B Corp (pre-normalised, plausible) are kept and shown
in a separate `real_disclosed` field.

**Not fixed:** the matching logic in `wikirate_fetcher.py` itself. Until then,
a whole real data source is unusable.

### 5.3 Real disclosed data does not feed pillar scores

Attempted "real data beats estimate" in `_pillar()` and reverted it — because
with WikiRate's bad values feeding the benchmark-band scorer, Apple's E jumped
to a flat 100.0–100.0. Upright/B Corp figures are on a different scale and
methodology, so they can't drop into the 0–100 pillar bands directly.

Needs a real mapping design before retrying.

### 5.4 Climate TRACE sector anchor unavailable for new markets

`_sector_anchor_claim()` needs a `market_climate_trace_mapping` row; the
smartphone market has none, and populating it is an LLM-driven step
(`market_climate_trace_mapper.py`) that has never been run for this market.
Only direct owner-name matches work (Apple matched; Samsung Electronics did not).

### 5.5 Metric benchmark bands are hand-set

The 0–100 bands (`scope_1_emissions` best=15 worst=250 per $M revenue,
`renewable_energy_pct` best=75, etc.) are chosen anchors, not empirically
fitted. Several E scores clamp at 100 because large-revenue companies fall far
below the "best" anchor once intensity-normalised — the score stops
discriminating at the top end.

### 5.6 Silent failure mode in metric estimation

`node_metrics_dry` / metrics-persist catch exceptions and return `{}`, so a
failed metric-estimation step looks identical to "no metrics found."
Motorola hit this in the v1 run — 0 core metrics, no error surfaced, only
discovered because it showed `no_data` in the JSON. Re-running fixed it.
The swallow is by design but needs a louder signal.

### 5.7 Rate limits

`zen_client.py` pins every call to `deepseek-v4-flash-free` with no model
rotation (deliberate — keeps results attributable to one model). The API was
fully 429-blocked earlier in the session and recovered on its own. Three full
10-company runs then completed with zero 429s at 4 workers.
